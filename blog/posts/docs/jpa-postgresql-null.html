当 JPA 原生查询遇上 PostgreSQL：一场 null 参数引发的"捉鬼"实录

缘起：一个看似普通的查询

最近在做一个 GIS 相关的项目，需要从 vector_data 表中根据三个可选条件进行组合查询：

  • dataId（Long，精确匹配）
  • keyword（String，全文检索）
  • propFilterStr（String，JSONB 字段包含匹配）

同时支持分页和按创建时间倒序排序。很典型的多条件动态查询，在 Spring Data JPA 中，我习惯性地写了这样一个 @Query：

@Query(value = "SELECT * FROM vector_data v " +
       "WHERE v.data_id = :dataId " +
       "AND v.keywords @@ to_tsquery(:keyword) " +
       "AND v.fields @> cast(:propFilterStr as jsonb) " +
       "ORDER BY v.create_time DESC",
       nativeQuery = true)
Page<VectorDataEntity> searchVectorData(...);

结果一跑，只要任何一个参数为 null，就报错：

错误信息
org.postgresql.util.PSQLException: 无法转换 bytea 到 bigint

我心想：JPA 不是会处理 null 吗？怎么直接崩了？

第一回合：为什么 null 会炸？

原生查询中，Hibernate 会把 :dataId 等参数原样传给 PreparedStatement。当参数为 null 时，JDBC 无法确定其 SQL 类型，PostgreSQL 的 JDBC 驱动默认将其映射为 bytea。接着执行 cast(bytea as bigint) 或 to_tsquery(bytea) 时，自然就类型转换失败。

核心矛盾：SQL 语法解析发生在参数绑定之前，即使条件逻辑上可以短路，但 cast 表达式本身已经被数据库"看到"并尝试解析了。null 参数的隐式类型成了 bytea，而 bytea 无法强转为数值或文本。

第二回合：SpEL 的假希望

Spring Data JPA 提供了 SpEL（Spring Expression Language）可以在 @Query 中访问方法参数。于是我尝试用 SpEL 来短路：

WHERE (:#{#dataId == null} OR v.data_id = cast(:dataId as bigint))

然而运行后发现，SpEL 只是决定了 是否拼接这个条件片段，但 cast(:dataId as bigint) 这个表达式仍然会被解析和编译。当 dataId 为 null 时，参数绑定后仍然是一个 bytea，转换依然失败。

我甚至尝试了直接 cast(:dataId as bigint) 或者先转 text 再转 bigint：

cast(cast(:dataId as text) as bigint)

这回 null 转 text 再转 bigint 居然不报错了！因为 bytea 转 text 是合法的（空文本），text 转 bigint 遇到空文本直接返回 null，不会报错。但问题是，我仍然无法优雅地处理"参数为 null 时不加条件"的需求。

第三回合：尝试规范方案——Specification

心想，干脆放弃原生查询，拥抱 JPA Criteria API。写了一个 Specification 动态拼接条件：

public static Specification<VectorDataEntity> dataIdEquals(Long dataId) {
    return (root, query, cb) -> dataId == null ? null : cb.equal(root.get("dataId"), dataId);
}

这样确实做到了"null 参数不生成条件"。但是全文检索和 JSONB 操作又成了新坑：

  • @@ 操作符需要调用 PostgreSQL 的 ts_match_vq 函数，或者用 function 模板；
  • @> 操作符需要 jsonb_contains 函数，或者 ?1 @> ?2 模板；
  • 处理 geometry/geography 字段时，Criteria API 几乎无法优雅映射。

最终我写出来这样的代码：

Expression<Boolean> match = cb.function("ts_match_vq", Boolean.class,
    root.get("keywords"),
    cb.function("plainto_tsquery", Object.class, cb.literal(keyword))
);

可读性极差，而且不同 PostgreSQL 版本函数名还不一样。更别提 geography 字段的 ST_DWithin 等操作了。

第四回合：JdbcTemplate 救场？

既然 JPA 这么费劲，那就直接用 Spring 的 JdbcTemplate 吧，完全掌控 SQL。

我快速写了一个 Repository，动态拼接 SQL，用 NamedParameterJdbcTemplate 绑定参数，确实清爽了很多：

if (dataId != null) {
    sql.append(" AND v.data_id = :dataId");
    params.addValue("dataId", dataId);
}

全部条件动态生成，null 参数根本不会出现在 SQL 中，类型转换问题彻底消失。

但是……当我看到实体类里的 geog 和 geom 字段时，人傻了。JdbcTemplate 默认只能映射基础类型，而 PostGIS 的 geometry 和 geography 需要注册自定义 ResultSetExtractor，将 PGgeometry 对象转换为 JTS 或 Hibernate 的 Geometry 类型。这工作量几乎等于重写整个 ORM 层。

而且项目里已经有大量基于 Hibernate 的地形函数调用（ST_Intersects、ST_Distance 等），换成 JdbcTemplate 意味着全部重写。权衡后，我决定放弃。

第五回合：回到原点，优化原生 @Query

折腾了一圈，我发现最初的原生 @Query 其实离正确只差两步：

  1. 用 SpEL 短路条件 — 确保参数为 null 时，整个条件被替换为 true，但要注意这并不能阻止 cast 表达式被解析，所以还需要第 2 步。
  2. 双重 cast 让 null 安全通过类型转换 — 对于 dataId：cast(cast(:dataId as text) as bigint) 在参数为 null 时返回 null，不会报错。对于 keyword：cast(:keyword as text) 保证 to_tsquery 收到的是 text 类型的 null，而不是 bytea。对于 propFilterStr：cast(:propFilterStr as jsonb) 同样需要显式转换。

最终可用的代码：

@Query(value = "SELECT * FROM vector_data v " +
        "WHERE (:#{#dataId == null} OR v.data_id = cast(cast(:dataId as text) as bigint)) " +
        "AND (:#{#keyword == null} OR v.keywords @@ plainto_tsquery(cast(:keyword as text))) " +
        "AND (:#{#propFilterStr == null} OR v.fields @> cast(:propFilterStr as jsonb)) " +
        "ORDER BY v.create_time DESC",
        nativeQuery = true)
Page<VectorDataEntity> searchVectorData(@Param("dataId") Long dataId,
                                        @Param("keyword") String keyword,
                                        @Param("propFilterStr") String propFilterStr,
                                        Pageable pageable);

几点改进：

  • 用 plainto_tsquery 代替 to_tsquery，避免用户输入特殊字符（&|!）导致语法错误。
  • JSONB 条件直接用 @> 操作符，配合 cast(... as jsonb)，简洁可靠。

复盘：为什么绕了这么一大圈？

方案优点痛点
原生 @Query 无处理简单直接null 参数导致 bytea 转换错误
加 SpEL 短路条件可选无法阻止 cast 表达式解析
双重 castnull 安全需要手动处理每个参数
Specification类型安全、可组合PostgreSQL 特有操作符支持差，地理字段噩梦
JdbcTemplate完全控制 SQL地理类型映射代价极高

结论：对于混合了全文检索、JSONB、地理数据的复杂查询，原生 @Query + SpEL 条件短路 + 双重 cast 是生产环境最务实的选择。虽然代码不完美，但胜在稳定、可维护、与 Hibernate 地理集成无痛。

给后来者的建议

  1. 不要迷信 JPA 能搞定一切。PostgreSQL 的强大扩展（全文检索、JSONB、GIS）往往需要你"稍微降级"到原生 SQL。
  2. 理解 null 参数在 native query 中的本质：它被当作 bytea，必须显式转换到你需要的类型。
  3. SpEL 只能控制条件的生成，不能控制表达式的解析。如果表达式包含类型转换，必须保证转换本身对 null 安全。
  4. 对于简单的动态查询，Specification 足够好；但一旦涉及数据库特有操作符，果断切回原生查询。
  5. PostGIS 的 geometry/geography 字段是 JPA 的舒适区，千万别用 JdbcTemplate 自找麻烦。

最后的感悟

这次"捉鬼"历程让我深刻体会到：技术的优雅和现实的复杂度之间，往往需要找一个平衡点。JPA 很美好，但 SQL 才是数据库的原生语言。适当使用原生查询，不是退步，而是务实。

希望这篇记录能帮你少走一些弯路。如果你也遇到了类似的"bytea 转 bigint"报错，不妨试试上面这个最终方案。
