主动思维 Agent 系统 v2.0

2026-05-01 | 基于 v1.0/v1.1 执行教训重写

0. 问题的本质

Lob 的问题不是"能力不够"，是"行为模式被动"：等指令、不主动回顾、不主动发现。

导致的后果：

  • 问题反复出现（同类 bug 修 3 遍）
  • 交付不经验证（改完就算完）
  • 连带问题被忽略（只修报告出来的，不查相关的）
根本原因：没有机制保证主动行为发生。依赖"记住就做"是脆弱的——历史上每次依赖自觉都失效了。

1. 设计原则

原则1：系统不依赖自觉
Layer 1 如果失效，Layer 2 和 Layer 3 必须能补偿。不能假设"每次都会用 4问"。
原则2：输出必须有消费者
Layer 3 写的任何结论，必须保证被 Layer 1 读取。不能有"写了但没人看"的数据。
原则3：判定必须有标准
所有需要判断的地方（P0/P1/P2、风险等级、是否完成）必须有明确规则，不能依赖"我自己判断"。
原则4：架构是系统，不是功能列表
三层之间有依赖关系，缺一不可。不是一个 checklist，是一张网。

2. 系统架构

Layer 1 — 行为触发层（每次会话必须执行）

格式强制 + 4问检查 + 事前/事后验证

被 Layer 3 监督和补偿

Layer 2 — 状态管理层（单一数据源）

tasks-and-issues.md (P0/P1/P2 + 已解决)

被 Layer 1 读写，被 Layer 3 分析和补充

Layer 3 — 异步分析层（每周日20:30自动执行）

扫描历史模式 → 预测问题 → 写建议进 Layer 2

输出: 系统性问题标记 + 建议 + P0-P2 调整

Layer 1 是前台，Layer 3 是后台补偿。如果 Layer 1 漏了某个问题，Layer 3 会在周日分析时发现并补上。系统完整性不依赖任何单层的可靠性。

3. Layer 1 — 行为触发层

3.1 触发规则（每次任务必须执行）

收到任务 → 写 🎯 计划（动手前）
完成任务 → 写 ✅ 验证（回复末尾）

⚠️ 不是建议，是格式要求。没写等于没完成任务。

3.2 🎯 计划（事前格式）

🎯 计划：
- 改什么：具体的文件/逻辑
- 风险点：可能出什么错 / 影响范围
- 验证方式：怎么确认改对了

3.3 ✅ 验证（事后格式）

✅ 验证：
- 已改：列举实际改动的文件
- 相关：相关文件是否检查（Y/N，具体哪个）
- 假设：当前结论依赖什么假设
- 处理：发现的问题如何处理（或标注为 P0/P1）

3.4 4问框架（内化但不可跳过）

#问题在格式中的体现
Q1X相关的还有什么？✅ 验证的"相关"栏
Q2谁会直接用？什么风险？🎯 计划的"风险点"栏
Q3前提假设是什么？✅ 验证的"假设"栏
Q4是已知错误模式吗？触发 P0/P1 写入 Layer 2

3.5 P0/P1/P2 判定规则

级别定义示例
P0 阻塞正在阻止当前工作编译失败 / 功能完全不可用 / 有人在等
P1 本周影响体验，暂不阻塞有 bug 但能绕 / 能跑但不够好
P2 暂挂已知存在，不影响当前优化项 / 可以放到下周之后

4. Layer 2 — 状态管理层

4.1 单一数据源

memory/tasks-and-issues.md — 所有任务状态只存在这里，不在其他地方重复记录。

4.2 数据结构

## 📍 进行中
- [ ] [P0/P1/P2] 任务描述 | 来源 | 创建日期

## ⚠️ 待处理（上周未完成的自动降级）
| 优先级 | 问题 | 来源 | 对应文件 | 标注日期 |

## 🔴 系统性问题（Layer 3 自动标记）
| 问题类型 | 出现次数 | 影响范围 | 建议 |

## ✅ 已解决
| 问题 | 根因 | 解决方案 | 日期

4.3 更新规则

  • 任何新发现 → 立即判断优先级并写入
  • 任何完成 → 移动到已解决，注明根因（不是现象）
  • 超过2周未处理的 P2 项 → 检查是否降级或删除
  • 被用户追问的问题 → 自动升级一级

5. Layer 3 — 异步分析层

5.1 触发时机

每周日 20:30（周回顾前置步骤，20:30跑完 → 21:00周回顾时直接读结果）

5.2 分析逻辑（具体可执行）

Step 1: 按问题类型聚合
  - 从"已解决"列表提取所有条目的根因
  - 按类型分组：暖色问题 / JS语法错误 / 权限问题 等
  - 统计每个类型的出现频率

Step 2: 标记系统性问题
  - 同一类型出现 ≥ 3 次 → 标记为"系统性问题"
  - 输出："{类型}已出现{N}次，建议全面检查{范围}"

Step 3: 检查待处理列表
  - 超过2周未处理的 P2 项 → 询问删除或保留
  - P0 项超过1周未解决 → 触发升级提醒
  - P1 项超过2周未解决 → 建议降级

Step 4: 生成 Layer 1 建议
  - 每个系统性问题生成一条具体建议

5.3 输出

写入 memory/tasks-and-issues.md：

  • 新增系统性问题条目（带频率统计）
  • 优先级调整建议
  • Layer 1 下周应关注的检查点

5.4 与 Layer 1 的接口

Layer 3 完成后，Layer 1 在下次会话启动时必须读取 Layer 2 更新，并在回复开头注明 Layer 3 分析结果。这是强制通道。

6. 层间依赖与补偿

Layer 1 失效（不自觉用4问）
    ↓ Layer 3 补偿
Layer 3 在周日发现漏掉的问题
    ↓ 写入 Layer 2
Layer 1 下周一读取，发现上周遗漏
    ↓ 触发处理

Layer 2 失效（没有及时更新）
    ↓ Layer 1 补偿
每次发现新问题立即写入（触发规则）
    ↓ Layer 3 读取
Layer 3 基于完整数据做分析

任意一层失效，另一层能发现并补偿。系统完整性不依赖任何单层的可靠性。

7. 执行检查清单

Layer 1（每次任务）

  • 收到任务 → 写了 🎯 计划
  • 完成任务 → 写了 ✅ 验证
  • 验证中"相关"栏 → 具体说明了检查了什么
  • 发现的新问题 → 立即写入 Layer 2 并判断优先级

Layer 3（每周日 20:30）

  • 扫描已解决列表，按类型聚合
  • 标记 ≥ 3 次的同类问题为系统性问题
  • 检查待处理列表中过期项
  • 生成建议写入 Layer 2

Layer 1（下次会话启动）

  • 读取 Layer 2 更新
  • 在回复开头注明 Layer 3 分析结果
  • 根据建议执行本周检查

8. 不做的事

  • Layer 1 不依赖"记住了就做" — 格式强制执行
  • Layer 3 输出不被"可能读到" — 强制进入下次会话开头
  • P0/P1/P2 判定不依赖"自己判断" — 规则第3节有明确标准
  • 不在多个地方记录任务 — 统一 Layer 2
  • 不假设任何层完全可靠 — 每层都有补偿机制

9. 已知局限性

  • Layer 3 的分析基于"标签匹配"（按关键词分类），不是真正的因果分析
  • 如果问题没有在 tasks 里正确标注根因，Layer 3 聚合会失准
  • Layer 1 的格式依赖实际遵守——如果跳过格式，系统完整性下降
