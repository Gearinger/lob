从"查地图"到"问地理"：Spring AI + PostGIS + Gemma 4 构建智能GIS系统

当大语言模型学会"看"空间数据，GIS操作的复杂度被一句话抹平

写在前面

传统 GIS 系统强大，但也很"重"。一个简单的需求——"找出距离河流 200 米内且坡度小于 15° 的地块"——在专业软件里往往需要：加载河流层 → 缓冲区分析 → 加载坡度栅格 → 重分类 → 叠加分析 → 制图输出。即便熟练用户，也要点几十次鼠标。

如果这一切可以变成一句自然语言呢？

近期，Spring AI 对 MCP（Model Context Protocol）的深度支持，加上 Gemma 4 26B 模型的原生函数调用能力，让这个想法离落地只有一步之遥。本文记录了我们基于 PostGIS + Spring AI + Gemma 4 26B 构建智能 GIS 助手的完整实践。

一、为什么是这套组合？

组件角色选择理由
PostGIS空间数据引擎成熟稳定、函数丰富、支持矢量和栅格
MCP工具调用协议统一接口，AI 可动态发现并使用工具
Spring AI智能体编排原生支持 MCP Client，SyncMcpToolCallbackProvider 一键注册工具
Gemma 4 26B推理大脑原生函数调用 + 256K 上下文 + 多模态 + 低延迟（4B 激活参数）

整套架构的核心思想：用自然语言驱动 GIS 工具链，而不是把业务逻辑塞进 Prompt。

二、系统架构：四层两协议

┌─────────────────────────────────────────────────────────────┐
│ 用户："帮我分析一下'地块A'周围500米内的商业用地分布"         │
└─────────────────────────────────────────────────────────────┘
 │
 ▼ MCP 协议（STDIO/SSE）
┌─────────────────────────────────────────────────────────────┐
│ Spring AI Client（调用层）                                   │
│ • 接收自然语言 → 发送给 Gemma 4 26B                         │
│ • 解析 model 返回的 tool_calls                               │
│ • 调用 SyncMcpToolCallbackProvider 中的工具                  │
└─────────────────────────────────────────────────────────────┘
 │
 ▼ MCP 协议（HTTP/STDIO）
┌─────────────────────────────────────────────────────────────┐
│ MCP Server（工具层，如 PG-MCP-Server）                       │
│ • 暴露空间分析工具：query_buffer, spatial_join, slope_calc   │
│ • 每个工具都包含清晰描述，供 AI 匹配                         │
└─────────────────────────────────────────────────────────────┘
 │
 ▼ SQL + PostGIS 函数
┌─────────────────────────────────────────────────────────────┐
│ PostGIS（数据层）                                            │
│ • 执行 ST_Buffer, ST_Intersects, ST_Slope 等                │
│ • 返回 GeoJSON 或统计结果                                   │
└─────────────────────────────────────────────────────────────┘

为什么分成两层？
Spring AI Client 与 MCP Server 可以是两个独立的 Spring Boot 进程（或一个进程内多个容器），通过 MCP 标准协议通信。这样工具可以单独扩展、升级，甚至用不同语言实现。

三、实战：从零搭建智能 GIS 助手

3.1 准备环境

基础依赖

  • JDK 17+
  • Spring Boot 3.4+
  • PostGIS 3.4+
  • Gemma 4 26B 推理服务（可通过 Ollama / vLLM / Workers AI 等暴露 OpenAI 兼容接口）

Spring AI 依赖（以 Gradle 为例）

implementation 'org.springframework.ai:spring-ai-mcp-client-spring-boot-starter'
implementation 'org.springframework.ai:spring-ai-openai-spring-boot-starter' // 用于调用Gemma兼容接口

3.2 第一步：部署 PG-MCP-Server

我们使用开源项目 pg-mcp-server（或自行实现）。它暴露两个核心工具：

  • pg_query：执行只读 SQL，返回 JSON
  • pg_explain：分析查询计划

配置 PostGIS 扩展上下文（postgis_context.yaml）：

name: postgis
description: PostGIS 空间函数集合
functions:
  - name: ST_Buffer
    description: 围绕几何图形构建缓冲区
    example: ST_Buffer(geom, 200)
  - name: ST_Intersects
    description: 判断两个几何是否相交
  - name: ST_Slope
    description: 根据DEM栅格计算坡度
    note: 需要栅格数据类型

启动 Server：

npx @modelcontextprotocol/server-postgres --connection postgresql://user:pass@localhost/gisdb

3.3 第二步：Spring AI Client 集成

application.yml

spring:
  ai:
    mcp:
      client:
        sse:
          connections:
            postgis-server:
              url: http://localhost:8080  # PG-MCP-Server SSE端口
    openai:
      base-url: http://localhost:11434/v1  # Ollama服务地址
      api-key: dummy
    chat:
      options:
        model: gemma4:26b-instruct-q4_K_M

关键配置类

@Configuration
public class McpClientConfig {

    @Bean
    public McpSyncClient postgisMcpClient() {
        // 通过SSE连接到MCP Server
        var transport = new SseClientTransport("http://localhost:8080");
        return new McpSyncClient(transport);
    }

    @Bean
    public SyncMcpToolCallbackProvider toolCallbackProvider(McpSyncClient mcpClient) {
        return SyncMcpToolCallbackProvider.builder()
            .mcpSyncClient(mcpClient)
            .build();
    }

    @Bean
    public ChatClient chatClient(ChatModel chatModel,
                                  SyncMcpToolCallbackProvider toolProvider) {
        return ChatClient.builder(chatModel)
            .defaultTools(toolProvider.getToolCallbacks())  // 一行注册所有MCP工具
            .build();
    }
}

服务层调用

@Service
public class GisAssistantService {
    private final ChatClient chatClient;

    public String ask(String userPrompt) {
        return chatClient.prompt(userPrompt)
            .call()
            .content();
    }
}

3.4 第三步：让 AI 理解空间操作

关键不在代码，而在 MCP 工具的描述质量。以 query_buffer 工具为例（定义在 PG-MCP-Server 中）：

{
  "name": "query_buffer",
  "description": "查找距离指定几何对象X米范围内的所有地物，并返回它们的GeoJSON。适用于"河流周围200米"等缓冲区查询。",
  "parameters": {
    "type": "object",
    "properties": {
      "geom_wkt": {
        "type": "string",
        "description": "中心几何对象的WKT格式，例如 'POINT(120.1 30.2)' 或 'LINESTRING(...)'"
      },
      "distance": {
        "type": "number",
        "description": "缓冲区距离，单位米"
      },
      "target_table": {
        "type": "string",
        "description": "要查询的目标图层表名"
      }
    },
    "required": ["geom_wkt", "distance", "target_table"]
  }
}
描述写得越精准，AI 调用准确率越高。这是一个"写文档"的活，比写代码更重要。

3.5 第四步：多步推理示例

用户提问：
"在'开发区'范围内，找出坡度大于 8° 且距离主干道小于 100 米的地块，生成统计报告。"

Gemma 4 26B 的推理轨迹（通过日志打印）：

1. 识别需要两个工具：slope_filter + buffer_query
2. 第一步调用 slope_filter(zone='开发区', min_slope=8)
   → 返回符合条件的多边形ID列表
3. 第二步调用 buffer_query(road_type='主干道', distance=100)
   → 返回缓冲区覆盖的地块ID
4. 对两个结果集做相交计算（工具 spatial_overlay）
5. 最后调用 generate_report(ids=...) 输出PDF

全部由模型自动编排，无需人工编写工作流。实测一个包含 6 步工具调用的复杂任务，端到端耗时约 45 秒（含 PostGIS 计算和模型推理）。

四、踩坑与优化建议

4.1 工具描述不能"太自由"

  • 坏例子："执行空间分析" —— AI 不知道什么时候该用它。
  • 好例子："根据给定的地块编号和距离，搜索周边兴趣点"。

4.2 小心 PostGIS 函数名暴露给 AI

直接暴露 ST_Buffer 等底层函数可能导致模型编造不存在的参数。推荐在 MCP 工具层做一层封装，例如 create_buffer(center_wkt, radius_meters)。

4.3 异步处理耗时任务

坡度计算、大范围缓冲区等操作可能超过 LLM 默认超时。解决方案：

  • MCP 支持 progress 通知，定期向客户端报告进度
  • Spring AI 侧使用 @Async 或 WebFlux 非阻塞调用

4.4 约束只读操作

PG-MCP-Server 的 pg_query 工具默认只允许 SELECT，这是生产必备的安全措施。避免 AI 误执行 DELETE 或 DROP。

五、效果评估与展望

我们在一个 50GB 的真实城市数据集中进行了测试（包含道路、地块、水系、DEM 等 12 个图层），选取了 30 个中高复杂度的自然语言查询任务。

指标结果
工具调用准确率（首次正确）83.3%
多步推理成功率（≥3步）76.7%
平均响应时间38 秒（含模型推理 + SQL执行）
用户满意度（1-5分）4.2 分

待改进点：

  • 当涉及坐标系统转换（如 Web 墨卡托 ↔ WGS84）时，模型偶尔会忽略。
  • 极长链条（>8 步）可能出现"中间结果丢失"，需要增加内存机制。

下一步计划引入 GraphRAG，将地理本体（行政区划、道路等级体系、用地分类标准）构建为知识图谱，与 MCP 工具调用协同，进一步提升复杂语义理解能力。

写在最后

MCP 的出现，让大语言模型不再是"只会聊天的鹦鹉"，而成为能够真正操控数字系统的智能体。对于 GIS 领域，这意味着：

  • 终端用户：用自然语言提问，无需学习软件菜单
  • 开发者：只需编写 MCP 工具描述，剩下的由模型编排
  • 数据工程师：PostGIS 仍是强大的计算引擎，无需迁移

而 Spring AI 提供的 SyncMcpToolCallbackProvider，让 Java 开发者用三行代码就能集成整个 MCP 生态。搭配 Gemma 4 26B 这样能在普通工作站运行的高性能模型，每个人都可以为自己的 GIS 系统加装一颗"AI 大脑"。
