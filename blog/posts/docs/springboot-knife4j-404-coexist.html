Spring Boot 中 Knife4j 与自定义 404 处理的完美共存

在 Spring Boot 项目中，集成 Knife4j 并实现统一异常处理（特别是捕获 404）是常见的需求。但在实践中，这两个目标常常会相互冲突：要么文档页面 doc.html 访问失败，要么自定义的 404 异常处理器不生效。

本文将带你深入理解这个问题的根源，并提供一个完美的解决方案，让 Knife4j 和自定义 404 捕获能够和谐共存。

🤔 问题现象：一个两难的境地

通常，我们希望在项目中实现以下两个功能：

  1. 集成 Knife4j：通过 http://localhost:8080/doc.html 访问美观的 API 文档页面。
  2. 自定义 404 处理：当用户访问一个不存在的 API 路径时，返回一个统一格式的 JSON 错误响应，而不是 Spring Boot 默认的 Whitelabel 错误页面。

为了实现第二个目标，一个常见的做法是在 application.yml 中添加如下配置：

spring:
  mvc:
    throw-exception-if-no-handler-found: true
  web:
    resources:
      add-mappings: false
  • spring.mvc.throw-exception-if-no-handler-found=true 的作用是，当请求没有匹配的处理器时，抛出一个 NoHandlerFoundException 异常。这样，我们就可以使用 @ControllerAdvice 来全局捕获它，从而自定义 404 响应。
  • spring.web.resources.add-mappings=false 的作用是关闭 Spring Boot 对静态资源的默认映射。

问题就出在这里：Knife4j 的 doc.html 页面及其依赖的 CSS、JS 文件，本质上都是静态资源。一旦我们将 add-mappings 设置为 false，Spring Boot 就不再自动为这些资源提供访问路径，直接导致 doc.html 返回 404。

这就形成了一个矛盾：要自定义 404 就必须关闭静态资源映射，但关闭了 Knife4j 又不能用了。

💡 解决方案：手动接管资源映射

这个矛盾的根源在于，我们将"静态资源映射"的控制权完全交给了 Spring Boot 的自动配置。解决思路也很清晰：关闭自动映射，由我们手动、精确地控制哪些静态资源可以被访问。

我们的目标是：只对 Knife4j 必要的资源开放通道，而对于其他不存在的 API 路径，则抛出 404 异常。

下面是完整的解决步骤：

1. 配置 application.yml

首先，保留上面的核心配置，并关闭默认的错误页面。

spring:
  mvc:
    throw-exception-if-no-handler-found: true # 让404抛出异常
  web:
    resources:
      add-mappings: false # 关闭默认静态资源映射

server:
  error:
    whitelabel:
      enabled: false # 关闭Spring Boot默认错误页面

2. 手动配置 Knife4j 静态资源

接下来，我们需要创建一个配置类，实现 WebMvcConfigurer 接口，并重写 addResourceHandlers 方法。注意，这里实现的是 WebMvcConfigurer 接口，而不是继承 WebMvcConfigurationSupport 类。后者会完全覆盖 Spring Boot 的 MVC 自动配置，带来更多不可预知的问题。

import org.springframework.context.annotation.Configuration;
import org.springframework.web.servlet.config.annotation.ResourceHandlerRegistry;
import org.springframework.web.servlet.config.annotation.WebMvcConfigurer;

@Configuration
public class WebMvcConfig implements WebMvcConfigurer {

    @Override
    public void addResourceHandlers(ResourceHandlerRegistry registry) {
        // 为 Knife4j 的页面和静态资源手动添加映射
        registry.addResourceHandler("/doc.html")
                .addResourceLocations("classpath:/META-INF/resources/");
        registry.addResourceHandler("/webjars/**")
                .addResourceLocations("classpath:/META-INF/resources/webjars/");

        // 如果你的项目还有其他静态资源（如 /static/**），也需要在此处添加
        // registry.addResourceHandler("/static/**")
        //         .addResourceLocations("classpath:/static/");
    }
}

通过这段代码，我们告诉 Spring："虽然关闭了自动映射，但对于 /doc.html 和 /webjars/** 这两个路径，请到 JAR 包中的指定目录去寻找资源"。这就像是为 Knife4j 单独开了一个"绿色通道"。

3. 全局捕获 404 异常

完成了资源配置后，我们就可以在全局异常处理器中放心地捕获 NoHandlerFoundException 了。

import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;
import org.springframework.web.servlet.NoHandlerFoundException;

@RestControllerAdvice
public class GlobalExceptionHandler {

    /**
     * 处理404异常
     */
    @ExceptionHandler(NoHandlerFoundException.class)
    public ResponseEntity<ResultBody> handleNotFoundException(NoHandlerFoundException ex) {
        // 这里的 ResultBody 是你的统一响应结构
        return ResponseEntity
                .status(HttpStatus.NOT_FOUND)
                .body(ResultBody.error(404, "接口不存在: " + ex.getRequestURL()));
    }

    // ... 其他异常处理方法
}

📝 总结

至此，我们成功地让 Knife4j 和自定义 404 捕获在项目中和谐共存。整套方案遵循了以下核心原则：

  • 精确控制：通过 add-mappings=false 关闭了宽泛的自动映射，避免了静态资源处理器"截胡" API 请求。
  • 手动开放：通过实现 WebMvcConfigurer 接口，为 Knife4j 必需的资源路径手动添加了映射。这确保了文档页面的正常访问。
  • 统一处理：结合 throw-exception-if-no-handler-found=true，让所有未匹配的 API 请求都能抛出 NoHandlerFoundException，并被全局异常处理器统一捕获和处理。

这套方案结构清晰，不仅解决了眼前的问题，也为未来项目中其他静态资源的管理提供了一个可靠的范本。
