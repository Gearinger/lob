主动思维 Agent 系统方案 v1.1

更新：2026-05-01 | 基于 v1.0 用户反馈优化

1. 问题定义

Lob（当前 agent）存在被动响应的问题：等指令，不主动思考。

根因：没有建立主动思维的习惯和机制，不是模型能力不足。

v1.0 的问题：设计过度、实现不足。大量精力放在架构图，但最关键的"如何确保 4问 被真正使用"含糊不清。

2. 核心优化

  • 优化1：4问 → 可执行动作格式（不是思考提示，是固定输出）
  • 优化2：Layer 3 触发时机明确（周日周回顾前定时跑）
  • 优化3：tasks 优先级排序（P0/P1/P2）
  • 优化4：增加"开始前检查"（事前预防 + 事后验证）

3. 三层架构

  • Layer 1：思维习惯（同步）— 每次动手前 + 完成后强制输出
  • Layer 2：状态维护（单一数据源）— tasks-and-issues.md（P0/P1/P2）
  • Layer 3：主动思维（异步）— 每周日 20:30 定时跑，结果推送 tasks

4. Layer 1 — 思维习惯（强化版）

事前预防（🎯 计划）

收到任何任务后、动手前，回复加上：

🎯 计划：
- 准备改什么（文件/逻辑）
- 可能的风险点是什么
- 如何验证

事后验证（✅ 验证）

每次改动完成后，回复末尾强制加上：

✅ 验证：
- [改了什么文件]
- [相关文件检查结果]
- [假设/风险是什么]
- [是否已处理]

4问（内化为检查框架，不是思考提示）

编号问题目的
Q1X相关的还有什么？（文件/数据/逻辑）连带性检查
Q2谁会直接用这个？会有什么风险？输出风险识别
Q3这个结论的前提假设是什么？假设检验
Q4这个是某种已知错误模式的实例吗？模式识别

触发条件（规则模式）

  • 新增/修改 .css / .html 文件 → 截图渲染验证
  • 修改共享组件（header.js / colors.css）→ 相关文件连带检查
  • 根据数据得出新结论 → 假设检验 + 反例检查
  • 修改计算逻辑/处理管道 → 结果敏感性分析

5. Layer 2 — 状态维护（优先级版）

单一数据源：memory/tasks-and-issues.md

优先级结构

## P0 — 阻塞（影响当前工作）
- [ ] xxx

## P1 — 本周需处理
- [ ] xxx

## P2 — 已知问题，暂挂
- [ ] xxx

## ✅ 已解决
| 问题 | 解决方案 | 日期 |

更新时机

  • 完成任何修复 → 立即更新（判断优先级）
  • 发现新问题 → 立即写入（判断 P0/P1/P2）
  • 每周复盘 → 扫一遍，处理过期项，升级/降级

6. Layer 3 — 主动思维（定时版）

触发时机：每周日 20:30（周回顾前 30 分钟）

任务流程

  1. 读 memory/tasks-and-issues.md
  2. 扫描 P0/P1 列表，判断是否有过期未处理项
  3. 扫描"已解决"列表，找重复模式（同类问题反复出现 = 系统性问题）
  4. 生成主动建议（"这个问题可能也会出现在X处"、"P2项 Y 建议升级为 P1"）
  5. 建议写回 tasks，标注优先级

整合到现有 cron

每周日 21:00 的"自我改进周回顾"已经在跑。Layer 3 sub-agent 作为该任务的前置步骤，20:30 先跑一次。

7. 针对不同领域的触发规则

UI/前端

  • 触发：新增/修改 .css / .html / 共享组件
  • 验证：截图渲染，对照设计规范
  • ✅ 验证格式：说明截图结果/肉眼检查结果

数据分析

  • 触发：得出新结论前 / 修改计算逻辑 / 给出建议
  • 验证：假设检验 / 交叉验证 / 敏感性分析
  • ✅ 验证格式：说明用了哪种验证方法、结论是否稳健
  • 常见错误模式：样本偏差、因果推断错误、幸存者偏差、数字解读偏差

代码逻辑

  • 触发：修改共享模块 / 重构核心逻辑
  • 验证：边界条件检查 / 依赖影响分析
  • ✅ 验证格式：说明边界条件是否覆盖、依赖影响范围
